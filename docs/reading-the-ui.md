# Reading the UI

Principle (epic #73): never display a state or a number that cannot be proven. When Agent Lens does not know, it says so instead of showing a plausible value.

## Views

- **Fleet / All**: the All view draws every watched session on one canvas. Each session is a dotted halo (its label gives runtime, workspace, status and cost; click it to zoom to the cluster). Sessions of the same project are grouped together.
- **Workspace zones**: when sessions of two or more projects are on the canvas, each project is drawn inside its own neutral rounded rectangle with a solid outline and a header chip ("Workspace payments-api · 2 sessions · 1 team"). A zone is a place, a halo is a group: halos are coloured circles (dotted for a session, dashed for a team or workflow), zones are rectangles that are never coloured by team. A session whose project is not proven (outside git, imported transcripts, a team that spans two projects) sits outside every zone: it is never placed in one by guess. With a single project, no zone is drawn. The zone is not a separate item in the graph list: the project is already read in each halo's announcement ("project payments-api"). Presentation mode masks the name.
- **Placement of agents** ([#554](https://github.com/j0hn-42/agent-lens/issues/554)): each session or team is laid out in a disc of its own around its orchestrator, and a sub-agent appears about 250 units from its parent. The disc grows with the agents that are **drawn**: with **Hide inactive** on, inactive (idle or finished) agents stop counting and leave the layout, so the agents still at work stay near their orchestrator. The phases of a workflow sit on a ring at half that radius. A disc never gets smaller than its agents need to sit side by side without touching. An agent that finishes does not resize its disc at once, so the other agents stay where they are (the orchestrator can still ease to the middle of the children that are still drawn, #151): the disc keeps the room until it would shrink by more than a fifth, or until an agent appears or the filter is toggled; the discs are then resized and the clusters move (eased, no jump) before they come to rest. The placement therefore depends on the filter. An agent shown again after it left the layout comes back next to its parent, not where it was last, and so does a hidden agent you select, hover or reach with the keyboard (it is drawn without resizing anything); an agent you dragged stays where you put it. Many agents at work still spread far out, since two agents are never drawn on top of each other.
- **Workflows and Teams**: a dashed halo groups agents. A *Team* is a Claude Code Agent Team; a *Workflow* is one run of the Workflow tool. The hierarchy is Session > Workflow or Team > Agent.
- **Comms**: message links between agents. Long dashes mean a message in flight, a solid line a recent one, a dotted red line an error. The badge is the message count; click a link (or its latest-message bubble) to read it in the link panel.
- **Context**: the project context of a session (`CLAUDE.md`, the memory index and the issue numbers they cite). It is loaded only when the panel opens or you refresh it, and a failure is shown as a failure. Below it, with the standalone relay, a table lists the open pull requests of the session's repository by branch with the state of their checks (the PR of the session's own branch reads "(this session)"), and the open issues no agent holds. "no checks reported" is not "passing", and "At least N ... shown" means the list is partial. See [node-inspector.md](node-inspector.md). A **CAPABILITIES** block lists the instruction files, skills and MCP servers of the session (see [Skills, plugins and memory](#skills-plugins-and-memory)). At the top, a **RESUME** block gives the command that reopens the session from a terminal (see [Resuming a session](#resuming-a-session)).
- **Session scope** (top bar, standalone app and dev relay): this workspace, one project, or all workspaces. The sentence next to the selector is what the relay reports it scans ("Scanning this workspace only (name)"; nothing is written on all workspaces), not what you asked: the selector only moves once the relay confirmed. On a single workspace an empty Sessions and agents list says that the scope is limited and how to widen it. A discovery ceiling that was hit (more than 500 transcripts in a folder, a transcript too large, the watch limit) is written next to the selector as "at least N": it is a partial view, not an absence. Choosing a project narrows the Sessions and agents list and the All view to it and leaves the relay scope as it is. Changing the scope reloads the view (a notice says so). See [relay-sources.md](relay-sources.md).
- **System**: the health of the machine that runs the relay (CPU, memory, swap, disk, load), opened with the top bar button, the command palette or **Y**. A metric that could not be read says "Not available" and has no meter, it is never 0; the severity (Normal, Warm from 85 %, Critical from 95 %) is in words and an icon. Local clients only, not available inside VS Code or in demo mode. See [system-stats.md](system-stats.md).
- **Sessions, Timeline, Files, Conversation**: the panels listed in the README.
- **One name per thing** (#372, the words come from `web/lib/ui-glossary.ts` and a test fixes them):
  - **Context** is the project panel (key P: project CLAUDE.md, memory, issues). The gauge of the model's tokens, in the agent card, the legend and the guided tours, is the **Context window**, never "Context" alone.
  - **Timeline** is the panel opened by T. The slider of the control bar is the **Playback position**.
  - **Sessions and agents** is the list opened by L: the top bar button, the Shortcuts dialog and the command palette use that name.
  - **Active only** (Sessions panel) lists the sessions heard from that are still followed and not marked finished, plus the selected one. It hides at once a session whose end was observed or that is no longer watched (its transcript passed the size cap, could not be read, or left the scan scope), and one never heard from: it has no time limit, unlike **Hide inactive** of the top bar, which keeps a finished session in the All view for 10 minutes after its last event. Its state is kept in this browser with the other interface preferences (the project and runtime filters of the panel among them), so a reload keeps it.
  - **Hide session** (the ✕ of a session row, or Delete on the row) removes the row from this page only: the session comes back on its next event or after a reconnect, and the toast offers Undo. Nothing is closed or stopped.
- **Settings** (#533): the gear button of the top bar, `,`, or the command palette opens one dialog split into four tabs instead of one long page; measured in the demo at 1440x900, 1024x768, 768x1024 and 1366x650, every tab fits without scrolling (the tallest panel is 608 px high in English, 625 px in French, so the dialog needs a window about 650 px high); on a smaller or shorter window, such as a small phone (320x568), the dialog scrolls vertically, never sideways; the live view, whose quota switch adds a row, was not measured. The dialog starts at the top of the window, so the tab list does not move when you change tab: **General** (Appearance: theme, language, hex grid, quota gauges; Sound), **Sessions and presentation** (Sessions and agents; Presentation), **Notifications and announcements** (Notifications; Screen reader announcements) and **Keyboard and preferences** (Keyboard; Preferences, with Reset preferences). The settings, their help and their rules are the same as before; a path such as "Settings > Notifications" still names the section, now inside its tab. The tab list is one Tab stop: Left / Right move between the tabs (wrapping), Home / End go to the first or the last, and the panel follows at once; Tab then goes into the panel. When the dialog opens, the focus is on the selected tab; Escape closes it and the focus returns to where it was. The last tab opened is kept while the page is open (a reload starts again on General): it is not a preference, it is not stored, and Reset preferences has nothing to reset about it. Leaving the Keyboard and preferences tab while "Reset now / Cancel" is asked cancels the question, nothing is reset. The command palette has one command per tab, *Settings: General*, *Settings: Sessions and presentation*, and so on (*Réglages : Général*… in French, named like the dialog), found by its English or French name or by a section title, accents optional; it opens the dialog on that tab. A tab whose settings are all absent (no notification channel and no announcement setting) is left out. The tab names are translated and may wrap on two lines; the tab list and the rows wrap rather than scroll sideways at 320 px or at 200 % zoom.
- **Hide inactive** ([#372](https://github.com/j0hn-42/agent-lens/issues/372)): one toggle of the top bar (row 1, after Notifications) and of **Settings > Sessions and presentation** replaces the former **Hide inactive agents** and **Show finished sessions**, which used two different thresholds. On (the default, the button is pressed and underlined), it applies exactly the two filters the code already had, nothing new: it hides the agents whose turn is over or that finished (idle at the end of a turn, complete, archived, or a member that reported done; an agent idle between two steps, in error or waiting for a permission stays, and so do the members of a workflow that still runs), and, in **All sessions**, the sessions marked finished whose last event is older than 10 minutes (the selected session and the sessions of a team at work stay; a session never marked finished is never hidden, however long it is silent). Off, every agent and every session is shown. The label, "Hide inactive" (*Masquer les inactifs*), gives no time window: the agents have none, only the session filter of All sessions has one, the 10 minutes of `ACTIVE_WINDOW_MS`, which the tooltip states. The accessible name is short and names only what the view hides: "Hide inactive: agents and sessions" in All sessions, "Hide inactive: agents" in one session or a team (*Masquer les inactifs : agents et sessions*, *Masquer les inactifs : agents*); the tooltip gives the rule for that view and what Off does. In All sessions, while it hides finished sessions, the button says how many: its description and its tooltip read "Finished sessions hidden: N" (*Sessions terminées masquées : N*), the count the former "Show finished sessions (N)" carried, taken from the same sessions the filter leaves out (in the project scope when one is chosen); nothing is said when none is hidden, when the filter is off or outside All sessions. The button keeps its place in the Tab order whatever its state and the view. A choice made with the two former settings is kept: only their default pair (inactive agents hidden, finished sessions not shown) becomes On; any other pair asked to see something they hid, so it becomes Off and nothing you chose to see disappears. The **Active only** filter of the Sessions panel is a different list filter (below), not this one.
- **Preferences and Reset preferences** (#372): the view preferences live in one place in this browser (local storage key `agent-lens:ui-prefs`): which of the Files, Conversation, Timeline, Stats and Cost panels are open, hex grid, **Hide inactive** (the one setting that replaced **Hide inactive agents** and **Show finished sessions**), the Sessions panel filters (**Active only**, project, runtime, branch), single-key shortcuts, the announcement level, the dock width, the remembered session, the chosen discovery scope, the **View** menu of the canvas controls (**Freeze motion**, the four **Calm** layers, **Pin cards**, **Hide unanswered calls after**) and the sound (on or muted). A choice made before they were grouped, under an older key of its own, is read once and kept (for the View menu: `agent-viz-pause-animations`, `agent-lens:calm-layers`, `agent-viz-never-hide`, `agent-viz-tool-expiry-s`; for the sound: `agent-viz-sound`). **Settings > Preferences > Reset preferences** asks first ("Reset now" or "Cancel"), then restores those defaults (the View menu back to moving layers, unpinned cards and 5 min; the sound muted) and forgets the older keys, and says "Preferences reset to their defaults". It leaves alone what is stored elsewhere: theme, language, notifications, presentation, session names, the legend and the width of the Sessions list.
- **Session export**: the ⤓ button of a session row saves it as a standalone HTML replay. The file states its own limits: events dropped before the export ("Incomplete history"), the number of secrets redacted (best effort), stream times, and agent states taken only from lifecycle events (otherwise "unknown"). See [session-export.md](session-export.md).
- **File conflicts**: two or more agents (of one session or of several) that modified the same file. A red dash-dot line with a diamond in its middle joins two such agents on the canvas, in every view where both are drawn (one line per pair, whatever the number of files). The Files panel lists the conflicts first (file and every agent with its number of edits) and tags the file row with the word "conflict"; with the editor available (VS Code), Enter on a conflict opens the file. The graph outline (screen readers) has a "File conflicts" list with the same sentences, an agent hidden from the canvas being named "not on screen". Only proof counts:
  - an edit is an `Edit`, `Write`, `MultiEdit` or `NotebookEdit` call whose success was observed. A failed or cancelled edit, or one whose end was never seen, proves no write and makes no conflict; a read never does;
  - the path must be absolute (normalised: separators, `.` and `..`, Windows drive letter). A relative path names a file only in a working directory that is not known, so two relative paths are never compared;
  - the edits are not required to overlap in time: a conflict says that two agents wrote the same file, not that they did so at the same moment. Edits made by other runtimes (for example Codex patches) are not recognised yet.
- **Review (pause) and switching session**: Review pauses the scene; events that arrive meanwhile wait in a queue, and Resume live reports how many. If you switch session while reviewing, the queue of the session you leave is not dropped: the position it had reached is kept with that session, so the events received while paused (and those received during the switch itself) are replayed when you come back. The view you switch to is live, so the review ends with a short notice ("Review ended: session changed") and the bar shows the live controls again; it never shows Review over a scene that is playing.
- **Live announcements (screen readers)**: state changes of the canvas are read in a polite region. A live failure of an agent ("Agent X failed") or a live permission request ("Agent X is waiting for permission") is read in a separate assertive region (with its session in the All view); a failed tool call ("Tool Bash failed for agent X") stays in the polite region. None of these is ever folded into a summary, but one pass reads at most three of them and then "and N more failures or permission requests" (N is exact). Only an agent heard from by a live event is announced as it happens; a state read from a history (replay after a reload, a session switch, an import) is told as "last known state: failed", is not urgent and counts in the summary like any other change. Beyond four other changes in one pass they are summarised ("N agent graph updates", real transitions only); messages between agents are counted apart ("N messages sent between agents", the number of new messages the links report, not the few that are listed). **Settings > Screen reader announcements > Announcement level** chooses how much is said, and is remembered in this browser with the other preferences. "Every change" (the default) is the behaviour above. "Important only" reads only live failures (agent or tool) and live permission requests: starts, completions, teammate activity, messages between agents and the last known states read from a history are not read out (they stay in the outline and the panels). A live failure of an agent and a live permission request are read at both levels, never summarised and never dropped; the cap of three sentences and the exact "and N more" apply to both. The roughly twelve polite live regions are not merged (not covered yet): the setting changes what the canvas announces, not which regions exist.
- **State markers** (agent rows of the Sessions panel, #381): the mark before an agent name has one shape per state, so neither its colour nor the pulse (gone under reduced motion) is the only cue: *Idle* a plain ring, *Thinking* a filled disc, *Calling tool* a larger filled square, *Waiting for permission* a larger dashed ring (the dashed ring of the canvas), *Paused* two vertical bars, *Complete* a check mark, *Error* a cross. An agent in *last known state* gets the plain ring of *Idle*. The row also says the state in words.
- **Renaming a session**: in the Sessions panel, the pencil button (or F2 on a row) gives a session a name of your own. Enter saves, Escape cancels, an empty name restores the original. The name lives only in this browser (local storage); it is never sent to the relay or written to a transcript. In the Sessions panel a renamed session keeps its original label in the tooltip and for screen readers; elsewhere (canvas, top bar) only your name is shown. If the session leaves the list while you type, the edit is dropped. The panel lists active sessions first, most recent activity first, and groups them by project.
- **Blank canvas after "Hide inactive"**: when every agent of the view is finished and the filter hides them all, the canvas says "N finished agents hidden" with a "Show" button that turns the filter off (it then shows every agent and every session). It appears only when each hidden agent is finished (an idle agent hidden too would make the count wrong), so the number is exact.
- **Hidden panels**: below 900 px wide (or when the panels cannot all fit), panels are full-width sheets and only the newest open one is drawn. A line under the top bar then says "N panels hidden: <names>. Close the panel shown to see <name>.", where the names are in opening order and the last one is the panel that comes back when you close the one shown. The names are the open panels the layout does not draw, so the list is exact (Context is named Context, not Files, even though both share one slot); nothing is written when none is hidden. On a very short window the line is still announced to screen readers but the sheet takes the room, so it may be covered. When the [Graph truncated](#graph-truncated) notice shows, it sits right under this line, and the sheet starts under both when there is room, even when it is the only open panel; the sheet is then shortened (it scrolls) rather than covering the notice. On a short window (or a narrow one where the top bar wraps), or when **Details** makes the notice taller than the room left, the sheet keeps only this line free and may cover the truncation notice, or the notice may cover the top of the sheet.
- **Top bar layout** ([#523](https://github.com/j0hn-42/agent-lens/issues/523)): from 1024 px wide the bar is two rows whose content never moves: row 1 holds the Sessions button, the scope, the connection state and the attention counter, then the view filters (Notifications, Hide inactive) on the right; row 2 holds the quota gauges, then the panel buttons and the tools (sound, full screen, Commands, Settings, shortcuts) on the right. There is one order for the keyboard at every width, row 1 then row 2. A row can still wrap inside itself when every optional control is shown at once on a narrow window (scope, attention counter, quota gauges, French labels). Under 1280 px the seven panel buttons (Files, Conversation, Context, System, Cost, Timeline, Stats) show an icon instead of their name; Commands and Shortcuts keep their text. An icon keeps the name of the button for screen readers and voice control ("Files", "Conversation (C)", "Context (P)", "System (Y)", "$Cost", "Timeline", "Stats"; in French "Fichiers", "Conversation (C)", "Contexte (P)", "Système (Y)", "Coût", "Chronologie", "Statistiques"). Hover or focus any panel button to read its tooltip: its name and shortcut, and for Context, System and Cost also what the panel shows (the Cost one gives the method of the cost estimate). Screen readers read that last kind after the name; a tooltip that only repeats the name and the shortcut is not read a second time. The tooltip stays while the pointer is on it, Escape hides it without moving the focus, and a click on the button hides it until the pointer comes back, so it never covers the panel that opens. An active panel button is underlined by a bar, not only coloured. The bar draws no summary text any more ([#523](https://github.com/j0hn-42/agent-lens/issues/523)): no tokens in context, no cost and no agent counts. The Cost panel draws the totals of the view, the Sessions panel those of each session, the inspector those of each agent. The agent counts of the view (`30 agents: 0 active · 4 last known · 26 done`, or `3 sessions · 12 agents` in All) are drawn in the header of the **Sessions** panel, with the same words; screen readers hear them in full ("4 last known state") there, and also in the bar, followed by the cost and the tokens in context of the view. The Cost panel is drawn on the canvas, which is not read, so while it is open it also carries its totals as text in a region named "Cost totals" (*Totaux du coût*), read in the interface language with the same figures and qualifiers as the drawing and the bar (*at least*, *estimated*, *not reported*; *au moins*, *estimé*, *non communiqué*). It follows the drawing: it gives the cost and the tokens in context of the header, then, in every view (one session or All), the unattributed row with its tokens and its cost read "about" for the drawn "~" (priced at the default rate, the model being unknown), and "estimated" when the drawing says so ("including 900k unattributed tokens (about $5.40 estimated)"; *dont 900k jetons non attribués (environ $5.40 estimé)*). When the panel draws nothing (no agent with a figure, nothing unattributed), the region is not there either, so it never reads "$0.00". It stays in full screen, where the canvas still draws the panel while the bar is hidden. The bar keeps its text, with the same wording: the Cost panel exists only while open, and the totals must stay readable without opening a panel ([#555](https://github.com/j0hn-42/agent-lens/issues/555)). Its unattributed part has the same wording, qualifiers and order as the Cost region above ([#576](https://github.com/j0hn-42/agent-lens/issues/576)): cost, tokens, then the unattributed part, in every view, and nothing when there are no unattributed tokens. It is no longer a bare "including $X unattributed", and it no longer depends on the cost being reported, as the drawing does not. The per-agent and BY TOOL rows of the Cost panel still have no text equivalent, on purpose: each agent row carries its own loss qualifier and its name is masked in presentation mode, and the same figures per agent are already read in the inspector, the graph outline and the Sessions panel, so a second list here would duplicate them without a proof of its own.
- **Top bar below 1024 px wide**: the panel buttons, the tools, the quota gauges and the view filters fold behind the **More** button ("More: panels, totals and filters", it says whether it is expanded); press it again to fold them. From 768 to 1023 px the Commands button stays in the folded bar, the panels stay docked and the controls keep their size (the drawers and the 44 px targets start under 768 px). Opening a panel from More folds it again, and closing that panel gives the keyboard focus back to More. While folded, screen readers still read the counts and totals; the filters are reached through More, and when **Hide inactive** is on the button says so: "More · 1 filter", its name naming it, with the number of finished sessions it hides in All sessions ("More · 1 filter on: panels, totals and filters (Hide inactive · finished sessions hidden: 3)"). Crossing 1024 px or 768 px keeps the keyboard focus in the bar. The Sessions button, the connection state and the attention counter stay in the bar. In the Timeline, the time labels are spaced for the panel width: fewer labels on a narrow panel, never two touching, and the last one is moved inside the edge rather than cut, or left out if it would then touch the one before.
- **Phone width (below 768 px)**: an open panel is a drawer the full width of the window, in the place of the sheets above (between the top bar and the playback bar, under the hidden-panels line and the truncation notice, which stay visible). It is a dialog: the keyboard focus moves into it and Tab cycles through it and, when they are drawn above it, the permission cards and the truncation notice (nothing else of the page); Escape or its Close button closes it and the focus goes back to the button that opened it (or to More when that button is folded). From inside a drawer the single-key shortcuts do not run. The controls of the top bar, the zoom block, the playback bar and the drawers' Close buttons are at least 44 x 44 px. On the canvas, the click and focus zone of a link-message bubble (and of its count chip) is at least 44 x 44 px too, the drawing staying smaller inside it; the zones of two bubbles never overlap, and a bubble hidden to avoid a collision is neither clickable nor reachable by Tab. Dragging and pinching the canvas have button equivalents: zoom in, zoom out and fit (which recentres the graph). Nothing forces an orientation. The connection state is the one the event stream proves (connected, reconnecting, offline); the view never says whether you are on the relay's machine or remote, because nothing in the stream proves it.
- **Quota gauges (top bar)**: at the start of row 2, two small gauges tell what is left of the Claude subscription quota: `5 h [bar] 38 % left` and `7 d [bar] 66 % left`. Hover or focus a gauge to read when it resets; Escape hides the tooltip. What they mean, when they say `quota: unknown for now` and how to turn them on or off is in [Subscription quota gauges](#subscription-quota-gauges).
- **Agents that need you**: the "! 2 agents waiting / 1 agent in error" button of the top bar (the "!" is decorative, screen readers read the words; in French "2 agents en attente / 1 agent en erreur") counts the agents waiting for a permission or in error. Each click selects the next one after the selected agent, waiting agents first, then wraps around; an agent of another session switches to that session instead. With a single agent it selects that one and does not promise a "next". Outside VS Code its tooltip adds that a permission is answered where the agent runs (its terminal or editor): the page draws no permission card there.
- **Command palette**: the **Commands** button of the top bar (a magnifier, with its name from 640 px wide; kept in the folded bar from 768 to 1023 px, not drawn under 768 px wide, where the folded bar has no room for it), or Ctrl+K (Cmd+K on a Mac), opens a search over five groups: *Actions* (play / pause, zoom to fit, full screen, hex grid, mute, the shortcuts dialog, settings, and the commands below that the view can run now), *Panels* (each panel, same names as the top bar; the Files panel is also found by "waste" or "repeated", for its *Repeated reads and calls* section), *Sessions* (including "All sessions"), *Agents* (the agents the Sessions panel lists, so finished agents hidden by "Hide inactive" are not offered) and *Themes* ("Theme: <name>" for each theme of Settings > Appearance, the one in use marked "current theme"). Type to filter (every word must match), Up / Down to move, Enter to run, Escape to close; focus returns to where it was. It is a modifier combination, so it works even with single-key shortcuts turned off, and from a text field, but not from inside another dialog. Only recorded facts are shown next to a name:
  - a session: runtime, project, branch, "current view", and "finished" only when the session list says it completed (or "imported - not live" / "indexed - not observed", as in the Sessions panel). It is never called active or running: nothing the palette reads proves that;
  - an agent: its role (Main, Subagent, Teammate) and its session, never its state, which may be older than the screen;
  - a shortcut next to a command is shown only while it works (none for single-key shortcuts when they are off);
  - some actions are listed only while they can run: "Go to the next agent that needs you" (first, with the text of the attention counter as its only detail) while an agent waits for a permission or failed; "Export this session as an HTML replay" while the session of the view has events in memory (not in the demo or a view that groups sessions); "Turn notifications on" / "off" while the browser allows them; the tour of the legend, under the same name ("Tour this session", or "Guided tour" in the demo), while one can start. While the relay serving the page accepts launches ([launch-security.md](launch-security.md)), "Find issues to launch for agent:<role>" (found by "launch") is listed once per role and session of the agents the view lists: it opens the card of the first agent bearing that role (named in its detail), where the open issues with that label have their **Launch** button and its confirmation. The entry does not say that such an issue exists: the card says so once it has read them. "Toggle presentation mode" and "Clear history" (undone like from the control bar, with the Undo of its notification) are always listed.

  Each group shows at most 8 matches, and the status line below the list says how many more there are ("keep typing to narrow") instead of pretending the list is complete. Session and agent names (and their details) carry `data-sensitive`, so presentation mode blurs them like in the other panels. Agents of another session are offered only while the view contains them: select that session (or "All sessions") first.
- **Folder prefix of session tabs**: the folder prefix appears when the sessions you have open come from two or more folders, a tab reads "folder / name" (the Sessions button in the top bar, and the sessions of a team in the Sessions panel) so two sessions called "fix login" can be told apart. The folder is the repository's folder name, proven by the git common dir (worktrees of one repository share it). Limits: a session outside git, or one under "Imported transcripts", gets no prefix, because no folder is proven; with a single folder nothing is added; under a project heading of the Sessions panel the prefix is not repeated, the heading already names the folder; a name that already starts with the folder is left as is. The prefix is display only: it is never written into the name you chose, and the canvas halos keep showing the session name and workspace as before.

The graph legend (bottom left of the canvas) explains the colours, shapes and lines that are on screen.

### The legend lists what is on screen

The legend does not list symbols the canvas does not draw (#244). A row appears only when the scene proves it, and a section with no row has no heading:

- an agent state, shape or runtime logo: at least one drawn agent has it (a hidden, folded or filtered-out agent proves nothing). A teammate ring, its working / idle / done mark and the orchestrator crown follow the same rule; a team row needs a team with two members on screen;
- a tool card line, a discovery card by type, a context part (non-zero for a drawn agent): the card or the part exists;
- a parent line: solid when the events confirm the link, dashed when they do not; a dispatch or return dot, a file conflict line, a "+N" or green badge on a folded branch, a session halo: drawn right now;
- a message link style: a link with at least one message in that state (in flight, recent, error, quiet); a bubble: a message bubble exists.
- a loop or repeat badge (*Loops and repeats*, #377): the badge is drawn on at least one agent of the scene.

The sentence under the title says how many symbols are listed ("N symbols on screen") or that nothing is on screen yet. **Show all symbols** (a toggle button, Tab then Enter or Space) lists the complete reference, on screen or not; the choice is not saved. A row whose symbol just left the scene (a message in flight, a particle, a tool card) stays listed for 10 seconds so the list does not jump under you. The guided demo keeps the complete legend, because its steps describe symbols the demo never draws.

### Tour this session

With at least one symbol on screen, a **Tour this session** button sits beside **Legend**. It starts a guided tour of the real scene (it is not shown in the guided demo, which has its own **Guided tour**). The command palette lists it too, under the same name.

On the first launch in a browser, a card "New to Agent Lens?" offers this tour above the control bar, as soon as the button above exists (not in the guided demo, full screen, presentation mode or under 600 px wide, where it would cover the canvas controls: these hide it without using it up). It is offered once: the browser remembers it (local storage, `agent-lens:tour-offered`) from the moment it shows, and when that storage cannot be read (a private window, blocked site data) it is not offered at all rather than on every visit. It never takes the keyboard focus; its text is read once by screen readers (polite). **Start the tour** starts it; **Not now**, or Escape inside the card, closes it and puts the focus on the tour button of the legend; starting a tour from anywhere closes it too.

- the steps are built when you start it from the symbols the canvas proves are on screen: your agents (main, sub-agent, runtime), each agent state present, tool calls, finished agents, who started whom, folded branches, file conflicts, teams, sessions, links, context parts and discoveries. A step for something that is not on screen does not exist, and no step talks about a symbol that is absent;
- a step points at a real agent (a ring follows it) or, for a symbol that no single agent shows (a link, a context part), at the matching legend section, which opens without changing your saved preference. The card names the agent it points at;
- the tour never pauses or seeks the scene: it stays live, and events keep arriving. A step is a snapshot: when what it explains has left the scene, the card says "This is no longer on screen" instead of going on as if;
- the card is the one of the guided demo: Previous, Next, **Go to step**, **Exit tour**, the arrow keys and Escape (inside the card only), and the focus returns to the button that opened it.

## Why this tool? and the causal chain of a failure

Click a tool call (or press Enter on its button in the graph list, or on the focused tool card): its popup has a **Why this tool?** disclosure (a native `<details>`: Tab to it, Enter or Space opens it). Every line is backed by an observed event; what cannot be proven is said so.

- **Reasoning observed just before this call**: the thinking that sits right before the call, in the same agent's own conversation, matched by the call's `tool_use_id`. Parallel calls of one batch share the reasoning that precedes the batch. Anything separated from the call by a result, an answer or a prompt is not attributed to it.
- **No reasoning observed just before this call**: the call is in the history and nothing precedes it. This is a finding, not an error.
- **Reasoning not disclosed by the runtime**: the runtime redacted the thinking; no text is invented.
- **Not provable: ...**: the call has no `tool_use_id`, is no longer in the kept history (conversations are bounded), or older messages were dropped. "Unknown" is never shown as "none".

A failed call also gets a **Causal chain of this failure**, an ordered list from the failure back to the prompt: the error text, the reasoning before the call, then for a sub-agent the dispatch that started it (who dispatched whom, with the full prompt and the parent's reasoning before the dispatch), and finally the **latest prompt observed before it** in the root agent's conversation. A hop needs the dispatch message with the same `tool_use_id` and a *verified* parent-child link; otherwise the chain stops with `Chain stops: ...` and says why. The prompt is an ordering fact (the latest one seen before), not a claim that it caused the failure. The derivation lives in `web/lib/tool-reasoning.ts`.

## What the action cards show

On the canvas, a tool card carries a small shape on its left that says what kind of action it is, so you do not have to read the label: a page (Read), a page with a plus (Write), a magnifier (Grep, Glob), a pencil (Edit, MultiEdit, apply_patch), a notebook (NotebookEdit), a checklist (TodoWrite), a globe (WebSearch, WebFetch), a speech bubble with a question mark (AskUserQuestion), a fork (Task, Agent sub-agent), and for Bash a prompt chevron and cursor, or, when the command line runs one of them (the first one wins): a node on a line (`git`), a rounded square with a node (`gh`), a snake (`python`), a flask (a test runner: `pytest`, `pnpm test`, `node --test`, `cargo test`), stacked containers (`docker`) or a parcel (a package manager: `pnpm install`, `pip install`). The shape comes from the tool name and, for Bash, from the command line only. MCP tools keep the generic card. While the call runs, the magnifier sweeps, the cursor blinks, the git node breathes, the globe turns, the bubble swells while an answer is awaited, a dot travels down the fork, the snake crawls and bubbles rise in the flask; with reduced motion (OS setting or Freeze motion) the glyphs are still. A shape says which command was issued, never that it succeeded.

A tool card or a discovery card is drawn only with its agent: when **Hide inactive** or a closed branch hides the agent, its cards leave the canvas too (a selected card keeps its agent shown), and **Fit to view** does not frame them. Tool cards are drawn above agent labels and message bubbles, so those texts are kept off the cards: a label moves aside, shortens to one line or is hidden, and bubbles fold into their count chip or are hidden, rather than sitting unreadable under a card. A halo label too long for its chip is cut with "…" and keeps its member count, e.g. "Session payments-api · ref… (4)". A label counts as drawn: its token line under the context bar ("4.3k estimated / 1M tokens") and its LEAD / MAIN pill are kept off the cards too, and a label hidden for a card takes its token line with it. Links and parent lines pass under agent labels: each line of a label sits on a small rounded plate of the scene background, so a line crossing the label is hidden only where the text is and drawn up to it (from the node's rim to the first line of text, and again past the label), never through the letters. The plate stays opaque while an agent appears or fades out.

**Fit to view** (and the automatic framing) frames the agents with their labels at the size they are drawn (enlarged below 100 %), their tool and discovery cards, the halos and the workspace frames, between the top bar and the row of canvas controls (Legend, Tour, zoom, View) that sits on the playback bar. Only floating UI that is not a bar (the Conversation pill, a toast, an open legend or View panel) can still cover part of the canvas.

**Zoomed out, text is hidden rather than shrunk.** Agent names and states, tool-card text, message-bubble text and the secondary canvas text (stats, cost pills, the context percentage, token counts, discovery text, particle labels, the model caption, phase titles) are not drawn smaller than about 10 px on screen; the secondary text keeps 11 px wherever it is drawn. Link bubbles still follow the zoom until their level hides them. The session, team and workflow titles above the halos keep their size at every zoom and move off the workspace headers and the collapsed Conversation pill. Below 100 % an agent's name and state keep that size instead of shrinking; where they would overlap, the labels of less important agents shorten to one line ("name · state") or are hidden first (the selected, hovered or focused agent, then a lead or main agent, then an agent in error, then active agents keep theirs). Under 35 % no agent label is drawn. Zoomed out under 100 % (and back above it once you pass 100 %), a tool card becomes its icon: the action shape, a ring for MCP, a dot for other tools without a shape, in the same colours, with the same dashes for an unresolved call, a cross in the corner for a failed call and the same spinning ring while it runs (with reduced motion, a still half ring instead). An agent's message bubbles become their count chip ("…2"), placed right of the agent's label. Under 100 % too, the context percentage, discovery text, particle labels and phase titles are hidden, and the model caption inside a node only appears zoomed in far enough for it to reach 11 px; token counts under an agent's label, and the stats boxes and cost pills you turn on, keep 11 px and are hidden under 60 %. A level that appeared is kept until the zoom falls 8 % under its threshold, so text does not blink while you zoom around it. Nothing is lost: names, states and tool calls with their outcome stay in the graph list read by screen readers, the tooltip and the popups give the details, and the Conversation panel keeps the messages.

Some tool calls have their own card content in the popup and the transcript. Every figure comes from the call's own input; when the input does not carry it, nothing is shown.

- **Edit / MultiEdit**: a sentence such as "3 lines replaced by 2" (lines of `old_string` and `new_string`, summed over the blocks for MultiEdit, with the block count). It counts the two strings, it is not a diff, and it describes the request, not proof that the edit was applied. The verb ("replaced by", "inserted", "text removed from N lines", since `old_string` may be part of a line) is used only when every block is of one kind; a MultiEdit that mixes them says "old: 3 lines, new: 2 lines". A MultiEdit whose blocks are incomplete, or a call whose strings are all empty, shows no summary. `apply_patch` keeps `+N -M`, counted from the patch text.
- **Write**: the number of lines of the content written. It does not say whether the file already existed, because the call does not prove it.
- **Read**: the line range requested (`lines 10–59`, or `from line 100` when only an offset was given), from the call's `offset` and `limit`. Nothing is shown when the call states neither.
- **Other runtimes**: tools named differently are drawn like the one they correspond to: Codex `shell` and `exec_command` (Bash), `update_plan` (TodoWrite), `web_search_call` (WebSearch); Copilot `bash`, `powershell`, `view` (Read), `edit` (Edit), `create` (Write), `grep` (Grep), `glob` (Glob), `web_fetch` (WebFetch), `task` (Task). The tool name shown is still the one the runtime reported.
- **apply_patch** (Codex): the patched files with their operation (add, update, delete), `+N -M` counted from the patch text, and the patch lines. The event keeps only the first 500 characters of a patch: when it was cut, the files seen are listed, the card says so, and no count is shown.
- **TodoWrite**: "N of M done" and "N in progress", counted from the list the call carries (a Codex plan counts the same way).
- **WebFetch**: the host of the URL on its own line.
- **Task / Agent**: the sub-agent type and the short description.
- **NotebookEdit**: the notebook, the cell and the edit mode, when the call states them.
- **Bash**: when the command runs `git` or `gh`, a pill names each subcommand as written (`git commit`, `gh pr create`), read from the command line itself. A second row lists Python, test, docker and package-manager calls (`python analyse.py`, `pnpm test`, `docker compose up`, `pnpm install`). A pill says the command was issued, not that it succeeded: the outcome is the tool's state. No exit code or duration is shown, because the events do not carry them.
- **Result pills** (tool popup and Conversation panel): once a call is seen to succeed, a pill shows what its own output proves. For a Bash command line that runs `gh`, a link **PR #N** or **issue #N** (opens in a new tab), when the output has exactly one line that is a plain `https://github.com/<owner>/<repo>/pull|issues/<n>` URL (`gh pr create` and `gh issue create` print it). A sub-path or an anchor (`/files`, `#issuecomment-…`), two different URLs, a failed call, or a URL on the last line of an output cut at the 200-character capture limit give no link. For Grep and Glob, **N files** when the output starts with the tool's own `Found N files` header; lines are never counted, because a cut output proves nothing.
- **File cards from a search** (canvas discoveries, #438): a Grep in `files_with_matches` mode (or with no mode set) that is seen to succeed and whose output starts with its own `Found N files` header gets one **File** card per path it lists, next to its tool card, at most 5 cards per call (`SEARCH_DISCOVERY.maxPerCall` in `web/lib/canvas-constants.ts`). Grep prints paths relative to the working directory, and each whole path line under the header counts: reading stops at the first empty line, line with a leading or trailing space, or `path:12:` line, and the last line of an output cut at the 200-character capture limit is dropped. A Glob's output is a bare list without the header, so its text proves nothing; its cards come from the structured result Claude Code records in the transcript (`filenames`, `numFiles`, `truncated`), forwarded by the extension only when `truncated` is false, every name is a distinct single-line string and `numFiles` equals the list length (at most 20 names forwarded, 5 drawn; the count shown is `numFiles`). A truncated or inconsistent result, or a source without that result (the hooks), gets no Glob card. The graph list, the tooltip and the popup say where a card comes from ("File listed by Grep, 1 of 47 files the call reported; 3 shown, 44 not drawn"); the paths not drawn are in no card, and the count is the header's for a Grep and `numFiles` for a Glob. A failed or cancelled call, a Grep in content or count mode, an output without the header, a path listed twice or a call without a `tool_use_id` (its cards would have no stable id) gets no card; a replayed result adds none.
- **Flow to the file cards** (canvas, #384): a thin line with an arrowhead runs from a Grep or Glob tool card to each file card it produced, and one small chip travels along each line for 3 seconds of session time after the call completed (`SEARCH_FLOW.chipWindowS`); then the line and arrowhead stay, static, as long as the card, including a card kept by Pin cards or the pause; a paused playback stops the chips at once. A line exists only when the card's `tool_use_id` and agent match a tool call that is on screen and complete; a card with no such call, or a call still running, failed, cancelled or expired, has none, and the line goes when the card fades. A call whose `tool_use_id` arrived only with its result has no line: its cards carry the id, the call does not, so no call matches them. At most 5 lines (and chips) per call. The direction, call to files, is carried by the arrowhead and by the text of the graph list ("File listed by Grep, ..."), never by the motion. With reduced motion, Freeze motion or the **links** layer calmed, the chips are gone and the lines and arrowheads stay. The lines carry no text.

## Themes

The **Theme** selector in **Settings** (the gear button in the top bar) offers nine themes, all dark:

| Theme | Pick it for | Look |
|---|---|---|
| **Catppuccin Macchiato** (default) | everyday use | the mid-dark Catppuccin flavor: soft slate-blue grounds, mauve accent |
| **Catppuccin Mocha** / **Catppuccin Frappe** | the Catppuccin palette you already use in your editor and terminal | the darkest and the lightest dark flavors (Latte, the light flavor, is not offered) |
| **Midnight** | long sessions, less eye strain | calm indigo and blue-violet, softer than Neon |
| **Graphite** | a neutral look | neutral grey, flat cards |
| **Neon** | the original look | cyan on deep blue-black, glass cards |
| **Ember** | the evening, reduced blue light | warm charcoal and brown, soft amber accent, almost no blue |
| **Anthropic** | a warm, neutral look | near-black warm greys, off-white text, orange accent. Inspired by the public colours of Anthropic; not an official theme, and it uses no logo |
| **High contrast** | low vision, bright rooms | pure black, white text (7:1 or more), yellow accent, strong white borders, a 3px focus ring |

The choice is stored in the browser (`agent-lens-theme`) and applied before the first paint. `?theme=catppuccin-macchiato|catppuccin-mocha|catppuccin-frappe|midnight|graphite|neon|ember|anthropic|contrast` picks a theme when nothing is stored. The system or VS Code light mode never switches the theme. The former light theme **Paper** was removed, and Catppuccin Macchiato is the default (it replaced Graphite): a stored `paper`, `light` or `dark` (and `?theme=` with one of these) now opens Catppuccin Macchiato, while a stored valid theme id, graphite included, is kept. In Midnight, Ember and High contrast the states (done, tool, error, delegate) also differ by lightness, not only by hue; the Catppuccin and Anthropic themes keep their own hues. In every theme a state is always paired with a word or an icon. Every theme gives each agent state its own colour: *Thinking* is never the idle colour and *Waiting for permission* is never the tool-call colour (roles `state-thinking` and `state-waiting`, checked to differ from every other state and to keep 4.5:1 as text). Neon's interface uses the violet and pink its canvas has always drawn these two states in. In Anthropic, *error* is a raspberry red (`danger` #ec698f), set apart from the brand orange that marks *idle*: the former coral red (#e5707a) was too close to it. Warnings that are not a permission wait (an incomplete total, a loop in the health verdict) use the warning colour, not the waiting one.

Catppuccin and the official palette: the colours are the ones of palette.json 1.8.0, mapped on the roles (void = crust, surface = mantle, surface-raised = base, edge = surface1, control-border and context-system = overlay1, ink = text, ink-muted = subtext0, accent = mauve, on-accent = crust, focus = blue, ok = green, warn = yellow, danger = red, delegate = lavender, info = teal, state-thinking = sapphire, state-waiting = pink). Every role value is the official one, unmodified. The only adjustments are in the Bash ANSI palette (the official normal and bright colours, 0 to 15), where a few entries are lightened toward white, just enough to keep 4.5:1 once dimmed: black and bright black (0 and 8) on the three flavors, bright red (9) on Macchiato, and red (1), blue (4), bright red (9) and bright blue (12) on Frappe. A few derived tints of the interface (error row, search highlight) are lighter-weight than before for the same reason.

Anthropic and the brand colours: Dark `#141413` is the surface, Light `#faf9f5` the text, mid grey `#b0aea5` the muted text, orange `#d97757` the accent (dark text on it), blue `#6a9bcc` the delegate colour. The brand green `#788c5d` is 4.48:1 on the raised surface, just under 4.5:1, so `ok` is lightened to `#8fa774`. The brand has no yellow, red or teal: warn, danger and info are warm derived colours, and the grounds (void, raised, edge, control border) are warm greys derived from Dark.

**The theme applies to the interface and to the canvas.** The toolbar, menus, dialogs, side panels (Conversation, Context, Cost, Files, Timeline, Stats), the legend, the inspector, the UI cards and the focus rings follow the theme. On the canvas, the colour of an agent's state (the ring, glow, centre icon, scan line, orbiting particles and waiting ripples of its node, the state word under its name, the glow of the scene behind the active agent) follows the theme too: it is the colour the panels (session list, timeline, control bar) give that state, so one state has one colour on every surface, and the graph legend's state swatches show that same colour. The canvas labels (agent names, session line, token count, stats box, LEAD / MAIN pill, the grey of a last known state), the links (lines, direction chevrons, count badges, message bubbles on links, links between sessions), the halos (outlines and labels of sessions and teams, workspace zones, phase labels), the discovery cards and the hex grid take the theme's colours as well; the hue of a session or a team is an identity colour and stays the same in every theme. The page background (#050510, the scene ground) and the rest of the scene (tool cards, message bubbles above agents, link particles, branch badges, file conflict marks, search flow, the tether to the detail card, bloom, cost overlay, the short flash when an agent finishes) keep the neon colours in every theme. Neon draws its whole scene as before (thinking violet, waiting pink). With High contrast, every state colour of the canvas keeps 7:1 or more on the scene background (#050510), and so does every text of the labels, links, halos and discovery cards, while each of their lines and shapes keeps 3:1 or more: a faint line is drawn more opaque, and a colour that cannot get there (a model tier colour, a team colour) is drawn in white. The hex grid stays faint: it is decoration. In the other themes state colours and canvas text keep 4.5:1 or more. A state is never told by its colour alone: its word is drawn under the agent's name, a finished agent has a dashed outline and an agent waiting for permission a dashed ring. In Catppuccin Frappe, *done* (green) and *tool call* (yellow) are the official green and yellow and sit a little closer to each other than the other pairs (in the panels and on the canvas alike): there, trust the word. Interface elements that sit above the dark scene stay readable: the top bar carries its own surface, the legend icons sit on a scene-coloured tile, and every focus ring keeps 3:1 or more against both the interface surfaces and the scene.

For contributors: the interface colours are defined by role in `web/lib/theme-tokens.json` (copy of the design tokens) and generated into `--lens-<role>` custom properties per `[data-theme]` in `web/app/themes.css` (`pnpm run gen:themes`). `COLORS` (`web/lib/colors.ts`) is the interface palette, rebuilt from the computed properties on every theme change: read `COLORS.<key>` when you render, never cache it at module load (use `themed(() => ...)` for a module-level table). `SCENE` is the frozen neon palette used by the canvas, the simulation and the page background for everything except the agent state colours, which follow the theme: they come from `sceneStateColor(state, theme)` (`web/lib/scene-state-colors.ts`, the state colours of the theme palette), and the draw loop reads the active theme on every frame with `sceneTheme()` and passes it in the draw options. Canvas code never reads `COLORS` and reads the theme only through that module (a test in `scripts/canvas-theme.test.ts` enforces both). Colour never carries a state alone: a word or an icon always goes with it.

## Honest values

| You see | It means |
| --- | --- |
| **Observed** | Agent Lens received events for it. |
| **Not observed** / "listed - activity not observed" | The session or agent is known (for example listed on disk) but no event was ever received. No state or activity is invented for it. |
| **Thinking** (agent state, Timeline "Thinking..." block) | A thinking block of the agent was observed, and nothing has happened since. A context reading, a prompt, an answer, a resolved permission or the end of a tool call never puts an agent in *Thinking*. |
| **Idle** between two steps (agent state) | After a tool call, a thinking block or a permission prompt ends (and no other call of the agent still runs), the agent shows **Idle** until its next event: what it does in between is not observed, so nothing is claimed. Its turn is not over, though: it stays on the canvas with **Hide inactive**, keeps its branch as it is (a branch you closed stays closed), stays the target of **Follow the active agent**, and no subtitle is written for it. Only the end of the turn makes it inactive. |
| **active** time (agent card, Sessions panel) | The sum of the observed thinking blocks and tool calls of the agent. It is a lower bound: the time between two steps (the model reading a tool result, writing an answer) is not observed, so it is not counted. "active time unknown" means nothing was observed. |
| **Xs alive** (agent card, canvas node) | The agent's age on the simulation clock: the current time minus its spawn, frozen at its end for a done agent (spawn to completion). The clock catches up with real time only when a live event arrives, so after a hidden tab the age lags until the next event. After **Clear history** the clock restarts at 0 and a kept agent reads 0 s alive until the next event brings back the session time, then its real age. It is not the active time. |
| "Not observed yet" (agent card) | The agent was announced but nothing has been seen from it. |
| "end not observed" (tool card) | The tool call started but its end was never seen. It is not shown as success or failure. |
| "last known state: X, silent for N min" | The agent sent no event for more than 5 minutes (the status is already "last known state" after 30 s). It is a silence, not a verdict: a long tool call or a long thought is silent too, so Agent Lens never writes "stuck". Shown in the agent card (inspector) and on the agent row of the Sessions panel, in whole minutes. |
| "waiting for permission for N min" | The last event of the agent was a permission request, and nothing answered it for more than 5 minutes. This is told apart from a plain silence because the agent itself said it was waiting for you. |
| **From history** / "history received" + a time (agent card) | The agent's status was read from a replayed history (the transcript read when the relay or the extension attached a session, or the replay after a reload or a session switch), not seen happening. The time is when this page received that history, not when the agent did anything. From the moment it is received, the status is only a *last known state* everywhere: the canvas node is greyed, the Sessions panel row says "last known state: X", the top-bar count puts it under "last known state", not "active". It is never shown as **Live** and never reported as silent; a screen reader hears "X shows a state read from history", not "no longer reporting". The next live event of the agent makes it live again. |
| **at least X** ("at least") | The total is partial: some part is absent, so the real value is X or more. It is never shown as a complete number. |
| **estimated** ("estimated") | The token count was computed locally, not reported by the runtime. |
| "no checks reported" / "checks unknown" (PR row) | gh listed no check for the PR, or its checks cannot be read. Neither is shown as passing. |
| "not reported" | The value is unavailable. It is not shown as 0. |
| **~$X** ("context cost estimate") | A cost: the tokens now in the context × a blended rate per model. An estimate even on reported tokens, never a bill. See [Cost](#cost-the--figures). |
| **unattributed** | A cost that cannot be tied to exactly one agent (unknown name, or several agents share it). It is listed apart, priced at the default rate, and included in the session total. See [node-inspector.md](node-inspector.md). |
| **conflict** (Files panel, canvas line) | Two or more agents each made at least one edit of the same absolute file that was observed to succeed. An edit not seen to succeed is never counted. |
| **Tokens of a file** (Files panel) | The sum of the cost of the calls that ended on that file, each call counted for its own file. It is qualified like every total: **estimated** when any part is estimated (shown `~12k` on screen), **at least** when a call on the file ended without a figure (shown `≥12k`; `tokens not reported` when no figure at all). A call still running or whose end was not observed adds nothing yet. The summary at the bottom adds the files with the same wording. The bar and the colour of a file are its share of the heaviest file: a heavy file is never drawn as an error. The read and edit counters count the calls started, failures and calls still running included; when fewer were observed to succeed, the row says how many did (`3 reads (2 succeeded)`). |
| **N steps observed** (Files panel, under a file) | The file's timeline: a disclosure (Enter or Space opens it) listing, oldest first, one step per Read (**read**), Edit / MultiEdit / NotebookEdit (**edited**) or Write (**written**) call on that file whose end was observed as a success, in the order those successes were seen, each with its agent and its `tool_use_id` (`call id not reported` when the runtime gave none). A failed or cancelled call, a call still running, or an end whose start was not seen adds no step; a replayed result of the same call adds nothing. The 50 most recent steps are kept: older ones are counted ("N earlier steps not kept") and still included in N. The count says **(incomplete)** when the relay could not replay some events. Commits are never shown: a `git add` or `git commit` command does not prove which files the commit holds (`commit -a`, a file staged earlier, a hook), and no event lists them. |
| **Git (observed)** (agent card: Branch, N commits observed, PR #n state) | Read only from the output of this agent's own shell calls whose end was observed as a success, and only when the command ran the subcommand that prints it and no other command of that line could have printed it (each part of the line runs that subcommand or a `git add`, which prints nothing): `git status && cat README.md` proves nothing. **Branch** comes from `git checkout` / `git switch` ("Switched to branch", "Already on"), the header of `git status` (or the first line of `-sb`), `git branch --show-current` run alone, or the `[branch sha] message` line of `git commit`; the line says which of these proved it, and **detached HEAD** when the output says so. A commit is listed only when the output of `git commit` shows that line (**amended** for `--amend`); a failed or cancelled commit, "nothing to commit", or a commit made by `git merge`, `rebase`, `cherry-pick` or `pull` is not listed. A PR state comes only from a gh output: **created** (the URL `gh pr create` printed; whether it is a draft is not in it), **merged** / **closed** (the line of `gh pr merge` / `gh pr close`; a queued `--auto` merge is not merged), or **open**, **open, draft**, **merged**, **closed** from a `gh pr view --json` object holding the number and the state. Each value is the state at the time of that call, never refreshed: a PR merged on GitHub later still reads **created**. "seen +m:ss" is the time since the agent appeared. Not proven, so not shown: which repository a `git` command ran in after a `cd` or `pushd` on the same line, a branch or a PR seen by another agent, a default branch (nothing observed, no strip). A command aimed at another repository (`-C`, `--git-dir`, `--work-tree`, `GIT_DIR=`, `GIT_WORK_TREE=`) or holding a `cd` / `pushd` is not read; the repository of a PR is the one its output names, else the one `-R` / `--repo` names on the gh line; a PR whose repository neither names reads **(repository not reported)** and stays a separate row. The 20 most recent commits and 5 most recent PRs are kept, the older counted ("N earlier commits not kept"); when the relay could not replay some events, the count says **(incomplete)** and the line **events lost: later changes may be missing** under the title qualifies the whole strip (the branch and the PR states may be older than the last ones). A replayed result of the same call adds nothing and never moves the branch back. A PR link says, to screen readers, that it opens in a new tab. |
| **Loading history (n/N)** | A burst of received events (switching to All, a relay replay) is being applied a few milliseconds per frame: n of the N events are on the canvas, the rest are not drawn yet. Screen readers hear the start and "History loaded (N events)" at the end. |
| **Time** and **Activity** (Sessions panel) | For a Claude Code session, Time counts from the start the transcript records (its first timestamp) and Activity from the last write of the transcript or of its sub-agent transcripts. Neither starts when the relay or the extension began watching: a session opened 3 hours ago reads 3 hours even if the relay started 2 minutes ago. |
| **≥2m 00s**, read as "watched for" ... "at least that long" (active) or "at least" ... "long" (completed), then "session start not recorded" (Sessions panel, Time) | The transcript records no start, so the duration only counts since Agent Lens began watching the session: the session is at least that old. |
| **imported - not live** (Sessions panel) | The session was read once from an imported transcript file (`--import`, see [relay-sources.md](relay-sources.md)). It shows what the file recorded up to its last line. It is never shown as active: whether it still runs elsewhere is unknown. Its agents are at best *last known state*, never current, and the inspector says *(imported transcript)* after the last event time. Imported sessions are grouped under **Imported transcripts**, which the project filter also offers. With **Active only** on, an imported session is listed only while selected. |
| **N active / N idle / N error** (top bar) | "active" only counts agents whose status is proven current and neither idle nor error; idle, error and *last known state* agents are counted apart, and done agents last. The screen-reader outline words a stale agent as *last known state: ...*, like the canvas. |
| **status unknown (relay offline)** (Sessions panel) | The relay is offline, so no event can arrive: an active session is no longer shown as *active*, and its duration stops at its last observed activity instead of growing. A halo whose working or waiting agents are all *last known state* says *last known: working* (or *waiting for permission*) rather than the bare status. |
| **Loop observed** / "No loop in the observed part" | The loop verdict (see [Loops and health verdict](#loops-and-health-verdict)). It never says "healthy": at best "No loop observed" over the calls it lists. |
| **COMPACTED** (Conversation row) | The runtime compacted the agent's context at that moment. The trigger and the size before are shown only when the transcript records them; "Cost not reported" always, since no transcript gives the cost of a compaction. See [Context compactions](#context-compactions). |
| **Not provable: ...** / **Chain stops: ...** | The reasoning or the next hop of a failure cannot be proven from the kept history (see [Why this tool?](#why-this-tool-and-the-causal-chain-of-a-failure)). Nothing is guessed. |
| `actual` / `configured` / `requested` (model pill) | Where the model shown comes from, strongest first. `requested != actual` means the runtime used another model. |

A silence is reported only for a status seen live and only for an agent that is not closed (done, failed or interrupted). A status that comes from a replayed history is never reported as silent: its age is not a wall-clock silence. For Claude Code sessions, the relay and the VS Code extension mark the events they read from a transcript history (`replayed`): the catch-up read when a session is attached, the sub-agent and teammate files already there, an imported transcript, and what is re-sent to a reopened panel. The page marks the events it replays itself. The initial history read of the Codex, Copilot, Pi, Gemini and OpenCode watchers is not marked yet ([#390](https://github.com/j0hn-42/agent-lens/issues/390)): their agents can still be shown as live right after the attach. The threshold is `SILENT_AFTER_MS` in `web/lib/canvas-constants.ts`.

A silence never ends a session. However long a session is silent (`pnpm test` running for 7 minutes, a permission left unanswered), its agents keep their last known state and its sub-agents are not closed. A session is marked completed (✓ in the Sessions panel, the **Session finished** notification) only when its end is observed: Claude Code's `SessionEnd` hook. A `Stop` hook only ends a turn: the orchestrator becomes idle, not done. Without the hooks, and for Codex, Copilot, Pi, Gemini and OpenCode, which report no end, a session is never marked completed by a silence: it stays in its last known state (for OpenCode, an archived session is the one exception, and a session silent for 10 minutes is no longer updated until new rows arrive).

## Repeated reads and calls

The **Files** panel opens with a "Repeated reads and calls" section, computed from the tool events already received (nothing is read from disk). It reports facts, not verdicts: a repeat may be intended.

| Row | It means |
| --- | --- |
| **read again N times, no edit seen in between** | The same agent read the same file, with the same offset and limit, N more times, and no Edit, Write or patch on that file (or a patch of unknown path in that session) was seen between the reads. A read of another range, or by another agent, is not a repeat: each agent has its own context. Nor is a read after a context compaction of that agent, or after a read of the file that was seen to fail or be cancelled: the content was not in its context. |
| **same Glob run again N times, no edit seen in between** | The same pattern and path, with no write seen in the session, nor compaction of that agent, between the calls. |
| **same Bash command run again N times, right after itself** | The same command (Codex: `exec_command`) with nothing else called by that agent in between. A command can legitimately change its answer, for example when polling a log. |
| **at least X tokens** / **estimated** | Cost of the repeats only (the first call is not waste). "at least" because some repeat had no reported cost; **tokens not reported** when none had (never shown as 0). |
| **N calls had no input details and were not compared** | A Read, Glob or Bash call arrived without the input needed to compare it. It is counted apart, not guessed. |
| **Tracking limit reached: this list is a lower bound** | More distinct calls than the ledger holds (4000) were seen; later ones are not tracked, so the list may be missing repeats. |
| **N more not shown** | Only the 20 costliest rows are drawn. |

Only Read, Glob and Bash/`exec_command` are compared, because their input summary keeps every argument. Grep and the other tools are never compared: their summary drops options, so two equal summaries would not prove two equal calls. Edits made through Bash (for example `sed -i`) or outside the agent are not seen, so a re-read after one can be listed. Each row is a button that opens the file only when the path is absolute and the host can open files (VS Code); otherwise it is plain text.

- **Badge on the canvas** (#377): an agent with at least one row here (one repeat is enough, the rule above; no threshold is added) carries a double chevron (») on a dark disc on the upper-left rim of its node, with the legend row *Double chevron on a node: repeated reads or calls observed*. A loop badge takes its place when the same agent also has a loop: one badge per node. The outline adds ", repeated reads observed" (or "repeated calls observed", or "repeated reads and calls observed", following the evidence) to the agent button and a line naming the costliest row ("Repeated reads observed: read again 2 times, no edit seen in between"), without the path. The legend and the tour give the exact rules: a file read again with no edit seen in between, the same Glob run again with no write seen in between, or the same Bash command run again right after itself. A badge is proven; its absence proves nothing (tracking limit, calls not compared, events not replayed).

## Delegation report

When the selected agent has sub-agents, its inspector ends with a **Delegation report** (#233): one entry per direct sub-agent (a grandchild is in the report of its own parent; Agent Team teammates are not delegations and are not listed), in the order they started. The sub-agent name is a button: Enter or a click opens that sub-agent's own inspector. The list of files read is a disclosure (Enter or Space opens it).

| Column | You see | It means |
| --- | --- | --- |
| **Tokens** | `12k`, **at least X**, **estimated**, **not reported** | The sub-agent's own token counter, qualified as everywhere else. |
| **Files read** | **N files** | Distinct files whose `Read` by this sub-agent was observed to succeed. The disclosure lists them (20 at most, then "+N more"). |
| | **N not confirmed** | Files whose `Read` started but was never seen to succeed (failed, cancelled, still running or end not observed). They are not counted as read. |
| | **none observed** | No `Read` by this sub-agent was received. It is not shown as "0 files": reads through other tools (Bash `cat`, Grep) are not seen. |
| **Duration** | **m:ss (measured)** | Measured by Agent Lens (the relay or the extension) between the dispatch and the return it observed live. It is not a figure the runtime reports with every return. |
| | **m:ss (recorded)** | A background sub-agent whose completion notice records its own duration: that recorded figure, not a measurement by Agent Lens. |
| | **not reported** | A return was received without a duration, or it came from a history replay or an imported transcript: there the duration was measured when the line was parsed, not while the sub-agent ran, so it is dropped. |
| | **no return observed** | No return of this sub-agent was received; no duration is computed from the clock. |
| **Result** | the start of the report | The first 280 characters of what the sub-agent returned to its parent, with "…" and "(full report in Conversation)" when cut. |
| | **Error: ...** | The return was flagged as an error. |
| | **No return observed yet** / **Finished, no return observed** | No return was received, whether or not the sub-agent is known to have finished. |

A sub-agent launched in the background (Claude Code's default, and always with `isolation: "worktree"`) is not finished by its launch: the tool result its parent gets right away only says it started. It stays running until Claude Code's task notification for it says `completed` (a return) or `failed`, `killed`, `stopped` or `cancelled` (an error), with the duration that notification reports. A notification without a status (an agent restarted after Claude Code exited) or with an unknown status finishes nothing. A finished sub-agent that resumes (relaunched with `SendMessage`, "Resuming agent") becomes active again from what is observed: a tool call it starts (one not seen before) brings it back at once; an assistant or thinking message of its own does so only after the prompt it received following its end. No new spawn is needed. A prompt alone, a late result or a bookkeeping event does not bring it back, nor does a late assistant or thinking message of the turn that already ended. Known limit: the last tool call of a turn can be read after the sub-agent's end, and then shows it active again until its next end. The next end is the one Claude Code's task notification reports after the resume (the `SendMessage` result names the agent it resumed); without that notification it stays active or "between two steps" and is never shown as finished.

A sub-agent already running when the relay or the extension attaches to the session (launched before a restart of the relay, for example) is drawn from the attach on, under the name its later events use ([#446](https://github.com/j0hn-42/agent-lens/issues/446)). It is drawn only when all of this is proven: its launch is in the session's transcript, the transcript shows no end for it (no final tool result for a sub-agent run in the foreground, no `completed`, `failed`, `killed`, `stopped` or `cancelled` task notification for one in the background, or a `SendMessage` resume after that notification; its file's metadata does not say the user stopped it), and its own transcript file exists and was written in the last 10 minutes (`ACTIVE_SESSION_AGE_S`); an older one appears on its next transcript line, if its launch still shows no end. It starts idle, read from history (its status is only a last known state); its next tool call or message seen live makes it live. A sub-agent whose end is in the history is not brought back, even if its file grows; a launch without a file is not drawn. At most 16 such sub-agents per session are drawn at the attach (`SUBAGENT_CATCH_UP_SPAWNS_MAX` in `extension/src/constants.ts`), in the order of their launches; any other one appears on its next transcript line, and the relay log says how many were held back.

A sub-agent whose link to its parent is not proven by the events (dashed on the canvas) reads **parent link not verified**. When the hooks see a sub-agent stop without its report, the result is the stop notice they relay (for example "general-purpose complete"), not a report.

## Subscription quota gauges

The two gauges of the top bar show the Claude Code subscription quota, as Claude Code itself reports it in its status line. Agent Lens does not compute it and does not estimate it.

- **What they mean.** `5 h` is the 5-hour window and `7 d` the weekly window. The figure is what is **left**, not what is used: `38 % left` means 62 % is used. The bar, the text and the screen reader value (a meter named "Quota 5 hours", "38 % left, resets at 16:40") carry the same number, rounded to a whole number for display. Under 25 % left a gauge also says "low" and under 10 % "critical", with an icon, never colour alone.
- **Reset time.** Hover or focus a gauge (Tab) to read when its window resets (the weekly one also names the weekday). Escape closes the tooltip without closing a panel or clearing the selection, and the pointer can move onto the tooltip to read it. Each gauge is one Tab stop.
- **Data age.** The figure is the last one Claude Code sent. Up to 5 minutes old it is shown as is; older, the gauge adds "updated N min ago".
- **`quota: unknown for now`.** Shown when no figure can be proven: after 30 minutes without an update, when a window's reset time has passed or is not credible (more than about 8 days ahead) so that window disappears, and when a snapshot has no valid window left. It is only said about a figure that existed and can no longer be trusted. A number we cannot prove is never kept on screen.
- **Nothing received yet.** For a Claude session, as long as no quota has ever arrived (Claude Code's status line is not wrapped, which is the default), the bar shows nothing about the quota: no gauge and no `unknown` text, since that is not a problem to fix. The way to turn it on stays in **Settings > Appearance > Quota gauges**, which says that without the status line wrapper no quota is shown.
- **Copilot and OpenCode** ([#532](https://github.com/j0hn-42/agent-lens/issues/532)). A Copilot or OpenCode session shows nothing about the quota: Copilot bills by usage since 1 June 2026 and its official API gives the consumption, not a remaining quota, and OpenCode has no subscription of its own (what is left depends on the provider you configured). A permanent "quota not available" would only repeat something that is not a problem, and showing a "left" figure would be invented. While a Copilot or OpenCode session is selected the bar shows nothing about the quota, not even the account's Claude quota. The rule is the same everywhere: the quota is drawn only when a figure exists, or `quota: unknown for now` when a figure we had can no longer be trusted. With no session selected and no figure, nothing is shown.
- **One account, latest value.** The quota belongs to the account, not to a session or an agent. While a Claude session or no session is selected, the gauges show the latest value received, whichever session sent it: with two accounts running at the same time, the last one received wins.
- **Hide or show.** **Settings > Appearance > Quota gauges** (on by default, remembered in this browser). The gauges only exist when the relay stream is the source: in VS Code, the demo and the guided tour there is none, and the setting is not offered. Under 1024 px they fold behind **More** with the panel buttons.
- **Turn the data source on.** The figures only arrive if Claude Code's status line passes them on, and that is **opt-in**: run `node scripts/setup.js --statusline`. It shows your current `statusLine` and the new one and asks `Apply? [y/N]` (`--yes` skips the question; with no terminal and no `--yes` nothing changes). Your own status line keeps running unchanged inside the wrapper. Undo with `node scripts/setup.js --restore-statusline`; uninstalling the extension restores it too. What is read and sent is in [Event sources](relay-sources.md#claude-code-status-line-subscription-quota-467).

## Context window (the "/ 1M" next to the gauge)

The used part of the gauge is a reading. The total is a window that is either **reported** by the runtime or **inferred** by Agent Lens, because Claude Code transcripts do not state it. Where it comes from, strongest first:

1. **Reported by the runtime** (Codex sends `model_context_window`): shown as is, even when the usage is above it.
2. **`CLAUDE_CODE_DISABLE_1M_CONTEXT=1`** (environment or the `env` of Claude Code's `settings.json`): every window is capped to 200k. In the VS Code extension this is read at start; for the relay and `node app/dist/app.js` it is read by `GET /status` (field `disable1MContext`, `false` when Claude Code is not watched), so the browser shows 200k as well.
3. **A `[1m]` suffix** in the model id: 1M.
4. **The model family table** (Opus, Sonnet, Fable, Mythos 1M; Haiku 200k; GPT 400k), 200k for an unknown model and 1M when no model is known yet.

A window cannot be smaller than what was used. When a reading is above the assumed window (a long session on a 1M model whose id was not recognised), the total grows to the next known size (1M), or to the usage itself beyond 1M, instead of showing more than 100%. The percentage then refers to an assumed window; the model pill and the table above say where it comes from.

**"window assumed".** In the interface, "assumed" is kept for a window that is a fallback, not for every inferred one: no model known yet, a model the table does not know (whether or not `CLAUDE_CODE_DISABLE_1M_CONTEXT` is set: the cap is an upper bound, not the size, and says nothing about a model the table does not list), or a window a reading has already overflowed. The qualifier goes with the window, never with the token count, which is a reading: **12k / 200k tokens, window assumed** on the canvas label and in the screen-reader summary of the node, **190k / 200k (95% of an assumed window)** in the inspector's **Context window** gauge. The percentage drawn above the node then says "assumed" too, and neither it nor the ring around the node is ever coloured or haloed as a warning or critical: how full a window of unknown size is cannot be proven. A window reported by the runtime, or inferred from a `[1m]` suffix or a family the table lists (capped or not), is shown without the word: the table is the documented source for those models, and marking it would put "assumed" on every Claude Code session.

## Cost (the "~$" figures)

Every cost in Agent Lens is a **context cost estimate**, never a bill: the tokens an agent holds in its context now, priced at a blended rate for its model (75% of the input price plus 25% of the output price per million tokens; the Sonnet-class rate for an unknown model). Transcripts do not give what each call was charged, so this is the only figure that can be computed, and it is marked as such:

- **On screen** a cost reads **~$2.10**: in the cost pills and the Cost panel, the session halos and the Sessions and agents list (the top bar no longer draws it, #523). The "~" stays even when the runtime reports its tokens (Codex): the tokens are a reading, the price is not. The qualifiers of the tokens are kept around it (**at least ~$2.10**, **~$2.10 estimated**). The tooltip of the **Cost** button of the top bar gives the method.
- **For screen readers** the same figure is said in words, "context cost estimate $2.10", in the node summaries, the halo announcements and the top bar (read after the agent counts, not drawn). The cost notification says "Context cost estimate reached ~$5.20".
- **What it misses.** It is the size of the context now, not a sum of the calls: it drops after a compaction (from ~$2.10 to ~$0.40 after `/compact`), it ignores cache reads (cheaper than input) and cache writes, and it does not add up the earlier calls that each re-sent the context. Read it as "what the current context weighs", not as what the session has cost.

The token total, **N tokens in context** (the Cost panel shows it as "N ctx tokens" for lack of room, and the graph legend defines "ctx tokens"), adds up what each agent's context holds now. It is not a consumption either, and it drops after a compaction too.

**The top bar summary was removed** ([#523](https://github.com/j0hn-42/agent-lens/issues/523), at the user's request): the short line of #497 (`30 agents: 0 active · 4 last known · 26 done · ≥~5.3M ctx tokens · ≥~$40.49 est.`), its popover and its key of symbols are gone. The agent counts moved to the header of the Sessions panel, the totals are in the Cost panel (drawn, and as text in its "Cost totals" region) and in the bar for screen readers only; see **Top bar layout** above.

## Context compactions

When the runtime compacts an agent's context (it replaces the conversation with a summary), the Conversation panel shows a **COMPACTED** row at that moment, in the agent's tab and in *All*. It is listed even when *Tool calls* is off, the search finds it, and it is a button like the other rows (Tab to it, Enter selects the agent).

- **Source.** Claude Code writes a `compact_boundary` system record in the transcript (`compactMetadata.trigger` and `compactMetadata.preTokens`); Codex writes a `compacted` record; Pi writes a `compaction` entry (`tokensBefore`). Nothing else is read as a compaction.
- **Trigger.** *automatic* or *manual, /compact*, only when Claude Code records `auto` or `manual`; otherwise *trigger not reported* (always the case for Codex and Pi).
- **Size before.** The context size before the compaction, *reported by the runtime* (`preTokens`, a positive whole number); otherwise *Size before not reported*. It is never estimated.
- **Cost not reported.** The summary call that performs the compaction has no usage in the transcript, so no cost is ever shown for it.
- **The gauge after it.** The local estimate restarts from the system prompt plus the compaction summary, then grows again. For Codex, the last total reported before the compaction is dropped (it measured the old context); the gauge shows the estimate until Codex reports a new total.
- **Limits.** A compaction written before Agent Lens attached to the session resets the estimate but is not listed. A boundary seen twice (same `uuid`) is listed once. A subagent's compaction is listed for that subagent and does not touch the session estimate. There is no before/after diff yet: the size after is only an estimate.

## Pi sessions

Pi coding agent sessions (#238) are read from their session files (`~/.pi/agent/sessions/--<path>--/<timestamp>_<id>.jsonl`, format of pi's `docs/session-format.md`, versions 1 to 3). What is shown, and what is not:

- **Shown.** The prompts, the assistant text and readable thinking, each tool call paired with its result by `toolCallId` (failed when the result says `isError`), compactions with their *Size before* (`tokensBefore`), and the session name given with `/name` as the session label.
- **Model.** The model named by each assistant message: the model that answered. A `model_change` entry is a selection (possibly a virtual model) and is not shown on its own.
- **Not shown.** Tokens and cost (the file records them, they are not read yet, so the gauge stays on the local estimate), system prompt updates, direct shell runs (`!command`), extension entries.
- **No sub-agents.** Pi documents none: every event belongs to the main agent and no child is ever drawn.
- **Unknown format.** A session whose header announces a version other than 1 to 3 is neither listed nor read, and the extension log says so once. A session whose id holds a dot (possible with `--session-id`), whose header has no absolute `cwd`, or whose file is a symbolic link is not listed either.
- **Branches.** Pi keeps abandoned branches (`/tree`) in the same file; they are shown in the order they were written, without the tree.

## Gemini CLI sessions

Gemini CLI sessions (#238) are read from their chat files (`<home>/.gemini/tmp/<project>/chats/session-<timestamp>-<id>.jsonl`, `<home>` being `GEMINI_CLI_HOME` when set). The format is the one written by `chatRecordingService.ts` of `google-gemini/gemini-cli`; it carries no version field, so records are read by shape and an unknown one is ignored. What is shown, and what is not:

- **Which sessions.** The directory name under `tmp/` is a short id from Gemini CLI's own project registry (it was the project hash in older versions), so it is never read. Every `chats/*.jsonl` is swept and the first record decides: its `projectHash` is the sha256 of the project root, compared with the sha256 of your workspace. A session started from a sub-directory of the workspace has another root, hence another hash, and is not listed. The record has no working directory: a session shows a folder only when the workspace hash matched, never otherwise.
- **Shown.** The prompts (a line starting with `/` or `?`, or empty, is not a prompt), the replies, the thoughts (subject and description), each tool call paired with its end, and the summary Gemini CLI saves as the session label.
- **Tool calls.** A call starts when it first appears in the file and ends when its `status` reads `success`, `error` or `cancelled`; the last two are drawn as failed. A call still `executing` has no end yet.
- **Model.** The model written on each reply, once per change. Nothing else is taken for a model.
- **Not shown.** Tokens and cost (the file records them, they are not read yet, so the gauge stays on the local estimate), info, error and warning messages.
- **No sub-agents.** Gemini CLI keeps a sub-agent in its own file under the parent session's folder; those files are not read and no parent link is guessed, so every event belongs to the main agent.
- **Rewinds and edits.** Gemini CLI rewrites a message in the file each time it changes, and can drop messages (`/rewind`) or edit them afterwards. A message is shown once. What was shown before a rewind stays shown: it did happen, and the file cannot say more. Edits to a message after the fact are not shown.
- **Not listed.** A file whose first record is not a metadata record, whose session id holds a dot, or which is a symbolic link; the old single-file `.json` sessions.

## OpenCode sessions

OpenCode sessions (#346) are read from OpenCode's own SQLite database (`<data>/opencode.db` for the latest, beta and prod channels (`opencode-<channel>.db` for any other channel), `<data>` being `$XDG_DATA_HOME/opencode` or `~/.local/share/opencode`; `OPENCODE_DB` overrides it: an absolute path is used as is, a relative one is resolved under `<data>`), opened read-only and polled; there is no hook. They carry the badge `OC` (accessible name "OpenCode") and the square brackets mark. What is shown, and what is not:

- **Which sessions.** Only sessions with rows written in the last 10 minutes (`ACTIVE_SESSION_AGE_S`) are followed, and at most 25 root sessions, the most recently updated first. History older than that window is not replayed when a session is attached. A session silent for more than 10 minutes is released, and followed again if new rows arrive. An archived session (`time_archived` set in the database) is released too.
- **Shown.** The prompts, the replies, the reasoning, and each tool call paired with its end.
- **No pending permission.** The database does not record a permission request waiting for an answer, so none is shown.
- **No end of session.** OpenCode reports no end, and a silence never completes a session: a session released after 10 minutes without rows is never shown as finished. Once released it is no longer updated; it keeps its last known state until new rows reattach it. Only an archived session is reported as ended.
- **No streaming text.** A reply appears once it is written to the database; the text still being streamed is not visible.
- **A late update can be missed.** To stay cheap on a large database, the relay reads again only a window of recent rows (the last 10 minutes, at most 2,000 rows per table) to see a tool call or a reply updated in place. A tool call it showed as pending or running, and a reply it showed before it was complete, are still followed after they leave that window (up to 500 per table): a tool silent for more than 10 minutes still ends when it finishes, even after the session was released. Any other row updated after it left the window is not read: the agent keeps its previous state. Such a change, when the relay finds it, is counted in the truncation notice of the session as "at least N updates not read" (a lower bound, never as ignored events). The same applies, when the relay starts, to rows of the last 10 minutes older than the 2,000 newest. A change in a session that is not followed at that moment is counted in the connection status of the VS Code extension ("N row changes not read outside the followed sessions") and, in the web page, next to the session scope ("OpenCode: at least N updates not read outside the followed sessions."). This sentence is written but not announced by screen readers: the count only grows, and announcing each rise would be noise. A session proved to be in another folder than the workspace is not counted (OpenCode keeps one database for every project, and such a session is never shown). Details in [Relay sources](relay-sources.md#opencode-346).
- **Database not readable.** When the database is not found (or cannot be read), the relay says so on `GET /status` and the sentence ("OpenCode: database not found.") is written next to the session scope selector. While it is shown the page reads `GET /status` again (after 5 seconds, then less and less often, at least once a minute), so the sentence goes away once the database reads. An empty session list alone never means that the database is missing. When OpenCode was not asked for (the relay's default `auto` mode), a missing database is the normal state of a machine without OpenCode and nothing is said, unless OpenCode is proved in use: `OPENCODE_DB` is set, the directory that should hold the database exists, or the database was read earlier in the same run. With `AGENT_LENS_RUNTIME=opencode` it is always said.
- **Unreadable rows.** A row the reader cannot use (an oversized or missing `data`, an unusable session id) is counted as malformed in the truncation notice of the session it belongs to, and a row that names no followed session is counted in the connection status of the VS Code extension ("N unreadable rows ignored outside the followed sessions") and, in the web page, next to the session scope ("OpenCode: at least N unreadable rows ignored outside the followed sessions."), with the same rules: not announced, and a session proved to be in another folder is not counted.
- **Platforms.** Linux (macOS not verified). On Windows the location is not resolved yet: set `OPENCODE_DB` to an absolute path.

## Project folders

Claude Code stores a session under `~/.claude/projects/<folder>`, where every character that is not a letter or digit of the project path becomes `-`: `/Users/me/my_project` and `C:\Users\me\my_project` give `-Users-me-my-project` and `C--Users-me-my-project`. Agent Lens finds the folder of your workspace and of its sub-projects with that rule, ignoring case on Windows. Past 200 characters Claude Code cuts the name and appends a hash that Agent Lens cannot recompute, so such a folder is matched on its first 200 characters.

## Skills, plugins and memory

The Context panel ends with a **CAPABILITIES** block (#242): what the selected session received or used, read from its main transcript (the file the relay already follows) when the panel opens or is refreshed. It is not what is installed on the machine: a skill or server that is installed but never reached the session is not listed.

| Group | Proof in the transcript |
| --- | --- |
| **Instructions loaded** | an `instructions` attachment (`files[].type` and the file's base name) or a `nested_memory` attachment (shown with the type `nested`). Only the base name is sent, never a path or the content. |
| **Skills**, grouped by plugin | a `Skill` tool call (`input.skill`, counted: "invoked N times") and the `skill_listing` attachments (`names`, union: "listed, no invocation seen"). The plugin is the namespace of the name (`plugin:skill`); a name without one is under **No plugin**. Skill arguments and descriptions are not sent. |
| **MCP servers** | `mcp__<server>__<tool>` tool calls, counted per server and per tool, and the servers named in an `mcp_instructions_delta` attachment ("announced"). Names are matched exactly: an announced name that differs from the prefix of its tools is shown twice rather than guessed. Tool inputs are not sent. |

| You see | It means |
| --- | --- |
| **Partial: only the first 32 MB ...** | The transcript is larger than the bound: only its head was read, so every count reads "at least". |
| "Lists capped ..." | A list reached 200 entries; later ones are not shown. |
| "No ... in the transcript" | Nothing of that kind was recorded. It does not say that the session had no skill or no server. |
| "The session transcript could not be read" | Missing, a symbolic link, outside the Claude projects folder, or a read error: the capabilities are unknown, never shown as empty lists. |
| "Not provided by this relay" | The relay is older than this view and sends no capabilities. |

Limits, on purpose: sub-agents (their own transcripts and sidechain lines) are not included; Codex, Copilot, Pi, Gemini CLI and OpenCode sessions and imported transcripts have no project context, so no capabilities either. The read is local, read-only and bounded, and the relay re-parses a transcript only when its size or modification time changed.

## Resuming a session

The Context panel starts with a **RESUME** block (#240): the command `cd '<cwd>' && claude --resume <session id>`, shown as text, and a **Copy** button that puts it on the clipboard. Paste it in a terminal on the machine where the session ran to reopen it in Claude Code. Nothing is run from Agent Lens and no request is made: the command is built in the page from the session list, so it works in VS Code as well. The result of the copy is announced ("Resume command copied" or "Copy failed: select the command and copy it by hand"); a failed copy is never reported as a success.

The working directory is quoted for a POSIX shell (bash, zsh, sh): every character between the single quotes is literal, and an apostrophe in the path is written `'\''`. Spaces, `$`, backquotes, `;` or `&` in a path are not interpreted.

The command is offered only when it can be shown to be right. Otherwise the block says why, and there is no Copy button:

| You see | It means |
| --- | --- |
| "only Claude Code sessions can be resumed" | The session comes from Codex or Copilot, or its runtime is unknown. |
| "an imported transcript comes from another machine" | The session was imported: its directory is not a local one. |
| "the working directory ... is unknown or not an absolute POSIX path" | No cwd was reported, or it is not a single-line absolute POSIX path (a Windows path, a relative path, a line break or a control character). |
| "the session id is not one Claude Code can take" | The id fails the relay's check (letters, digits, `.`, `_`, `:`, `-`, 128 characters at most) or starts with `-`, which `claude` would read as an option. |

### Go to terminal (VS Code only)

Inside the VS Code extension the RESUME block also has a **Go to terminal** button (#240). It asks VS Code to open an integrated terminal whose working directory is the one the extension recorded for the selected session. Nothing is typed or run in that terminal: you choose what to run, for example by pasting the resume command.

- The page sends the session id only, never a path. The extension looks the session up itself, and refuses when it does not know the session, when its directory is unknown, is not an absolute single-line path, or no longer exists (a warning says which).
- The button is offered for every runtime that reports a directory (Codex, Copilot and Pi included), not only for Claude Code, and never for an imported transcript. It does not exist in the browser app: a page cannot open a terminal.
- The status line says "Asked VS Code to open a terminal ...": that the request was sent is all Agent Lens can prove. Whether the terminal opened is shown by VS Code itself.

### Permission requests (VS Code only)

With operator control on ([operator-control.md](operator-control.md)), a permission request Claude Code is waiting on appears at the top right of the canvas with the tool, the session, the whole input and its deadline, and three buttons: **Approve**, **Deny** and **Redirect**. **Redirect** opens a dialog for a text Claude receives with the refusal, so it can change course; the text is required, and it is never kept on screen nor written to the journal (only its length is).

| You see | It means |
| --- | --- |
| "Sending the decision…" | Your click left the page; the extension has not answered yet. |
| "Decision sent: approve" (or deny, or redirect) | The extension handed your decision to Claude Code. **Sent is not applied**: whether the tool ran (or the refusal reached Claude) only shows later in the transcript. |
| "Deny applied" / "Redirect applied" | After your deny or redirect was sent, the session showed live the end of **that very call** (same session, same tool call id), in error, not interrupted, and its result contains the refusal: the deny text, or the beginning of your redirect text. That is the observed refusal. A failure reported by the hook (`[FAILED]`), another error text, an approval, a call that is "not identified" and a decision sent from another panel are never shown applied. |
| "Decision sent from another panel" | A decision for this request was handed to Claude Code, not from this page. |
| The request disappears, with an announcement | It ended without a decision: the deadline passed, Claude Code stopped waiting (answered in the terminal, call interrupted), control was turned off or the panel could no longer decide. Claude Code then shows its usual prompt. |
| "Input truncated" | Only the first 64 KiB of the input are shown; the SHA-256 given is the one of the whole input. |
| `\u202e` and other escapes in the input | An invisible character of the real input, shown as its escape instead of being applied to the text. |

**A detail popup never hides a pending decision (#536).** When you open the popup of a tool call or of a discovery while a permission request is shown, the popup is placed so that it covers no part of the cards: neither their title, nor **Approve** and **Deny**. Press Tab from the popup: the keyboard reaches **Approve** and **Deny**, each one is drawn, has a focus indicator and is not covered. Press Escape in the popup: it closes, the request stays, and the focus returns to the element that opened the popup. What is measured: `web/tests-a11y/e2e/popup-permission.e2e.ts` opens both kinds of popup over a real permission card (a fake extension bridge posts the request to the demo app) at 320x568, 390x844, 768x1024, 899x700, 1024x768 and, for the 200 % zoom heights, 640x360 and 640x300, in Chromium. Not proven: a real device, a browser other than Chromium, and popup anchors other than the simulation's tool position.

## Graph truncated

When the normalizer discarded something for the selected session (or, in a view that groups sessions, for the sessions that view counts added up: the ones All shows, or those of the team), a "Graph truncated: N events ignored, M nodes dropped" notice appears under the top bar, followed by ", at least K updates not read" when the source changed rows that the reader was no longer following (OpenCode, see [OpenCode sessions](#opencode-sessions); K is a lower bound and these are not counted as ignored events). **Details** lists the counters by reason under two headings: **Losses** (earlier events not replayed by the relay, when there are some, then events ignored, malformed inputs, nodes dropped and updates not read) and **Adjustments (not losses)** (fields shortened or clamped, duplicate events skipped: nothing was left out of the graph for them). Duplicates skipped and fields shortened alone do not trigger it. The cross is "Dismiss truncation warning". A dismissal is kept for the browser tab (sessionStorage), per view (All, a team or one session), with the total it was dismissed at: reloading the page in the same tab does not show it again, a new tab does. It comes back when more is lost in that view; since the relay's figure is a total since the relay started, a page loaded later on a relay that kept receiving events of a long session can show it again. It also comes back when the total of the view is lower than the one it was dismissed at: the relay was restarted (its figure starts again from 0) or the graph was reloaded, so this is a new loss, not part of the one dismissed. Dismissing it in All also covers each session All counted, at that session's own total, so opening one of them right after does not show it again. When the browser refuses the storage, a dismissal lasts until the page is reloaded. While a loss is known, a short line stays in the header of the Sessions panel, under the agent counts, even after a dismissal: "⚠ at least N events not replayed" and/or "N events ignored, M nodes dropped", with the numbers of the notice for the same view, in the language of the interface. Its **Show notice** button reopens the notice with **Details** expanded and puts the focus on **Details** (only then: when the notice comes back on its own later, after full screen for instance, the focus stays where it is). While the notice is closed and a loss is known, the Sessions button of the top bar carries ⚠ too, so the loss stays visible with the panel closed; screen readers hear it with the button name ("graph incomplete, losses listed in the Sessions panel"), and it goes away while the notice shows. Adjustments alone draw neither the notice, nor this line, nor the mark. While it shows, the graph is partial: counts, "none observed" and "no loop" verdicts only cover what was kept. The same notice also covers the events the relay could no longer replay when the graph was first loaded (its buffer evicted them or its replay cap left them out): "Graph incomplete: at least N earlier events were not replayed by the relay". Only the first connection of a graph counts: the graph was empty then, so none of those events had been received, and N is a lower bound. The relay's figure is a total since the relay started, not what a given page lacks; a later reconnection that keeps the graph already received most of those events live, so its new figure is ignored and the first one stays (the hole it described is still there, also while the link is down). What a reconnection adds is what the cut link itself lost: the page tells the relay the last event it received, and the relay counts, per session, the events after it that it can no longer give back (evicted from its buffer while the link was down, or left out by the replay cap); they are added to the count of their session. It is a lower bound too, and only when the relay kept running: a relay restarted while the link was down numbers its events anew, so nothing is added for that cut (see [relay-sources.md](relay-sources.md)). It starts again after a scope change, which reloads the view. For one session it is that session's own count; for All it is the count of the sessions All shows (the ones it leaves out while **Hide inactive** is on, or that a project filter leaves out, are not counted), and the events of sessions the relay no longer names are added only when All shows every session; for a team it is the count of the sessions of that team only. A session the relay does not name is never reported as incomplete on that ground, and events a restarted relay never saw cannot be counted. The count and the loop verdicts above stay "at least" / "incomplete" while it applies. In the agent card, the figure is the count of that agent's own session, whatever the view: never the total of All or of a team, never the events of sessions the relay no longer names, and nothing for a session the relay does not name. There, the tool count and the tool errors read "at least N", "0 tool errors" becomes "no tool error observed (incomplete)", and in the delegation report the list is named "at least N sub-agents" for screen readers, files read say "at least N files", "none confirmed (incomplete)" or "none observed (incomplete)", and the result says "No return observed (incomplete)" (or "Finished, no return observed (incomplete)" for a sub-agent seen to finish) instead of a final answer; a line gives the missing count. In the Files panel, the figure is the one of the notice (the selection: one session, All, or the sessions of a team), file conflicts read "at least N conflicts", and when none is seen it says "No conflict in the observed part" with the same line; the file count reads "at least N files", and an empty list says "No file observed (incomplete)" instead of "No files yet". A conflict that is shown stays proven; only the totals and the absences are qualified. On the canvas, the Stats box under an agent reads "at least N tools" (or "no tool observed (incomplete)") and the cost pill and the agent's row in the Cost panel read "at least ~$X", from that agent's own session only, like the agent card; the box grows to hold the longer text (never past 240 px: a line that would still be wider drops its duration, never its qualifier). The graph outline read by screen readers says "at least N tool calls" or "no tool call observed (incomplete)" and the same lower-bound cost for the same agents. The Cost panel header (cost and tokens) and the totals the top bar reads aloud are lower bounds ("at least") when any agent of the view, or any usage in it that belongs to no agent (the unattributed remainder), belongs to a session that lost events, each session counted once; a figure that is "not reported" stays so. In the Files panel, "Repeated reads and calls" reads "at least N times" for each repeat, "No repeat observed (incomplete)" when none is seen, and adds the line giving the missing count. Nothing changes when no loss is known. The cost on a session or team halo (and the same figure in its outline heading) reads "at least ~$X" when one of the sessions of the agents it adds up lost events. A token or context figure is different: a context reading is absolute, and a reading the page never received (a compaction that shrank the context, for instance) could have lowered it as well as raised it, so it is never called a lower bound. The token line under the context bar of an agent and the percentage above the context ring add "(incomplete)", the token line of the outline and the context window of the agent card add "(last reading, incomplete)", from that agent's own session only; the label space reserved on the canvas is the one of the longer text. The bar itself and the ring are drawn from the same last reading (the top bar draws no number any more, #523). In the Sessions panel, the tokens of an agent row and of the branch, session and team family totals that count such a session are marked "?" instead of "≥" (spelled "last reading (incomplete)" or "incomplete" for screen readers), their costs are marked "≥" like the other costs, and the totals carry "(incomplete)", whose explanation names the replay loss among its causes and says the real figure may differ. The notice is left out in full screen like the rest of the chrome. A separate live region announces it when it appears, and again when leaving full screen brings it back; nothing is announced in full screen, where no notice is drawn. Dismissing it puts the focus on the Sessions button of the top bar.

### Context readings replaced in the relay replay

The relay's replay replaces a context reading of an agent by a later reading of the same agent taken at the same instant (a tool call emits up to three in a row), when nothing shown can tell them apart: the current context of each agent, the gauge at every instant of a review, the agents and their states are the same. These replaced readings are not lost events and are not counted in "at least N earlier events were not replayed by the relay"; the replay keeps more of the session for the same caps. Readings of different instants are all kept. A [session export](session-export.md) of a replayed session has no row for a replaced reading. Rules and measures: [relay-sources.md](relay-sources.md#replay-buffer-context-readings-replaced-at-the-same-instant-567).

## Presentation mode

For demos and streaming. Start it with `V` (or Settings > Presentation); stop it with `V`, `Esc` or the "Presentation mode - V to stop" button under the top bar. It is announced ("Presentation mode on/off") and never starts by itself: only the three options below are remembered in this browser (`agent-lens:presentation`), the mode is not. Each option can be turned off in Settings > Presentation.

- **Subtitles of transitions**: a caption at the bottom of the canvas for each state change of an agent, for example "Main agent: Thinking -> Calling tool Read". Only proof counts: a subtitle is written when this page saw the change happen live. An agent idle between two steps of its turn gets no subtitle: the next observed step is reported from the last one ("Calling tool Read -> Calling tool Edit"). Nothing is said about the state that was already there when the mode started, and nothing about replayed history, imported transcripts or an agent never heard from live. A caption stays 7 seconds; when several changes arrive together, the most recent one is shown. It is for the audience: it is not a live region, so a screen reader is not interrupted.
- **Mask sensitive data** (on by default): free text is hidden, never replaced by a plausible value.
  - On the canvas, tool-call arguments and results, message bubbles, discovery cards, link messages, particle labels, agent names, session and team names (halo labels, the cost panel) are drawn as bullets of the same length. Counts, costs, states, tool names and context gauges stay, because they come from the events and carry no prompt or path.
  - In the panels, Conversation, Files, Context, Timeline, the link panel, the tool and discovery popups, the Sessions and agents list, the selected-session label in the top bar, the agent name in its card and the canvas hover tooltip are blurred and cannot be selected.
  - Subtitles name an agent by its role ("Main agent", "Sub-agent", "Teammate") instead of its name or prompt.
  - Not covered: the text read by screen readers (the graph outline, announcements), the browser tab title, notifications, and anything you copy from a panel before starting the mode. Masking is a screen filter for the audience, not a privacy boundary; check a scene before you share it.
- **Follow the active agent**: the camera centres on the agent that worked last (thinking, calling a tool, waiting for a permission or idle between two steps of its turn, seen live), keeping your zoom. With no such agent it stays where it is. Panning or zooming yourself pauses the follow until another agent takes over; the automatic fit is off while the option is on.

## Notifications

The **Notifications** button in the top bar turns notifications on or off; **Settings > Notifications** chooses what triggers them. Nothing is asked of the browser until you turn them on, and the choice stays in this browser (local storage).

| Trigger | Fires when | Default |
|---|---|---|
| **Agent waiting for a permission** | an agent starts waiting for you to allow a tool | on |
| **Agent in error** | an agent itself is reported in error (no event observed by Agent Lens sets this state yet, so it cannot fire today; a failed tool call does not count: the agent usually handles it and goes on; it shows in the tool error count of the inspector) | on |
| **Session finished** | a session you were watching goes from active to completed: its end was observed (Claude Code's `SessionEnd` hook), a silence never fires it | off |
| **Cost threshold reached** | the context cost estimate of the view (the total of the Cost panel) crosses the amount you set (USD, above 0, up to 10 000), once | off |

- **Where it shows.** In a browser, a system notification appears only while the tab is hidden (the tab title also carries the number of blocked agents). In VS Code, the webview asks the extension, which shows a native message unless the Agent Lens panel is the focused view. The extension checks and caps every message and shows at most one per trigger every 2 seconds.
- **Only what is new.** A trigger fires on a change, never for what was already there: the first state after loading is a baseline, a session already finished in the history is not announced as finished, and nothing is sent while the history is replaying.
- **Only what is proven.** A permission or error is counted only while the app can prove it (see the states above). A cost that is unknown never triggers; a lower bound triggers once it has proven the threshold is reached and the message says *at least*; an estimate says *estimated*. The wording is the one of the top bar.
- **Keyboard.** Every switch and the amount field are reachable with Tab; Space toggles a switch. An invalid amount is refused with a message and the previous threshold stays in force.

## Loops and health verdict

Agent Lens looks for two loop patterns in the tool calls it received (#230), per agent:

- **Repeated identical calls**: the same tool called 3 times or more in a row with the same input (same arguments, whatever their order).
- **Read → edit → failure cycles**: a file is read, edited (`Edit`, `MultiEdit`, `Write`, `NotebookEdit`), then the edit itself or the next call fails; 3 such cycles in a row on the same file. A call that succeeds after the edit, or whose end was never seen, breaks the streak.

The **Health** section of the inspector gives the verdict of the selected agent, the evidence of each loop (one line each; hover a cycle line for the full path) and the verdict of its session. The Sessions panel marks a session row with "⟳ loop observed" only when a loop is proven; it says nothing otherwise.

| Verdict | It means |
| --- | --- |
| **Loop observed** | At least one pattern above was seen in the events. It may be over: the verdict covers the kept history, not only the last minutes. |
| **No loop observed (N tool calls)** | Every call of the kept history was compared and nothing repeated. |
| **No loop in the observed part** | No loop seen, but the history is partial: calls without input data cannot be compared ("n of N comparable"), or older messages were dropped (the last 200 conversation messages per agent are kept), or the relay could not replay earlier events of the session ("at least N earlier events of this session not replayed by the relay", see [Graph truncated](#graph-truncated)). A count that may have started before the dropped part reads "at least". |
| **Not enough activity to judge** | No comparable tool call was received. |

Limits, on purpose: only what the events prove is counted, so a loop can be missed (calls without input data, another tool between two identical calls, an edit followed by a read of another file) but is not invented. A tool that polls on purpose (the same `Bash` status command three times) is reported as a repeat: read the evidence before acting. Only sessions whose events are in the current view have a verdict.

- **Badge on the canvas** (#377): a node whose verdict is **Loop observed** carries a circular arrow (⟳) on a dark disc on the upper-left rim of the hexagon (the crown holds the upper-right one), with the legend row *Circular arrow on a node: loop observed* under **Loops and repeats**. No badge is drawn for the other verdicts: there is no "healthy" mark. The screen-reader outline adds ", loop observed" to the agent button and a line with the evidence (at most two findings, the others counted, "at least" kept); a read, edit, failure finding names the base name of the file, and the outline is not masked by presentation mode). The badge is static (it never spins: the loop may be over), drawn at every zoom, faded with a stale or archived node, and not announced live. It is not clickable: select the node for the **Health** section.

To add a string, add its key to **every** locale in `web/lib/messages.ts`; `scripts/messages.test.ts` fails on a missing key, a different `{placeholder}` or a French text that is still the English one. `web/tests-a11y/i18n-no-mixed-languages.test.tsx` renders Settings (each notification state, an invalid threshold included), the canvas controls, the Sessions panel (columns, agent rows in each state, the announcement of agents that stop reporting), the agent card, the command palette and the legend in each locale and fails on any rendered string (visible text, accessible names, tooltips, descriptions) that is not a value of the current locale's catalog or of an explicit allowlist of proper names and symbols; a subtree that stays English is left out only if it carries the `data-i18n-exempt` attribute, and it declares `lang="en"` as well. The guided tour (card, offer, buttons, every step) and the titles of the panels are rendered by the same test, with no exemption and no allowlist of their own. When you translate a new surface, add it to that test. Still English for now: the rest of the top bar, the other panels (Conversation, Context, Cost, Files, Timeline, Stats), the Σ totals, the relative times and the agent counts of the Sessions panel, the shortcuts dialog, the presentation-mode banner and its announcement, and the attention counter. To add a language, extend `LOCALES` and fill the table.
